是什么

“A context window measures how many tokens — the smallest building blocks, like part of a word, image or video — that the model can process at once.”

窗口之外的内容对模型等于不存在——不会自己“想起来”，只有下次推理前被重新放进来才有用。聊天机器人“失忆”，多半是旧话被挤出了窗口。

02

解剖：窗口里装了什么

01
🧭 系统提示 · System Prompt
人设、规则、背景知识。通常放最靠前的位置、最“权威”，但上下文太长时也可能被“淹没”。
02
💬 对话历史 · History
一问一答的消息记录。聊得越久越占地方，常见策略是“挤出最旧的，留下最近的”。
03
📄 资料与检索 · Documents
上传的文件、RAG 召回片段、网页抓取内容——不是越多越好，塞进来就要占注意力。
04
🛠️ 工具与返回 · Tools
工具/函数定义 + 每次调用结果。Agent 每“动”一步，都会往窗口里回填一截新内容。
05
🎯 本次输入 · Query
用户最新的问题或目标，是模型最需要聚焦的“现场指令”。

输入 + 输出都算在窗口内：一段长回答也会消耗窗口额度。窗口 = 全部上下文 + 正在生成的内容。

03

为什么有上限

⚡ 注意力是“两两比较”

Transformer 让每个 token 都与其他所有 token 计算相关度，n 个 token ≈ n² 次比较。窗口翻一倍，算力大约翻四倍。

💾 KV 缓存吃显存

生成时要把已见 token 的 Key/Value 向量缓存进 GPU。上下文越长缓存越大，显存和带宽先到顶。

🎓 主要在“短文”上训练

模型训练时见过的序列有限；超出训练长度要靠位置编码插值硬撑，越长越容易“失准”。

限制一半来自数学（注意力复杂度），一半来自硬件（显存/带宽），还有一半来自“长了也不一定用得好”——见下一节。

04

窗口越大 ≠ 用得好

两个实证现象

关键内容放开头或结尾最稳，埋在长上下文的“中间”最容易丢。

Lost in the Middle（Liu et al.，2023）：模型对出现在开头的信息最好（首因），对结尾的次好（近因），对中间的显著变差——准确率画出来是一条 U 型曲线。

Source · arXiv 2307.03172《Lost in the Middle》
开头：高中间：低 ⚠️结尾：中高

↑ 示意：U 型（颜色越深越好用）

🥀 上下文腐烂 · Context Rot

Anthropic 在上下文工程文章中指出：token 越多，模型精确回忆信息的能力越下降——所有模型都如此，只是下降斜率不同。性能是“缓坡”而不是“悬崖”。

📉 注意力预算有限

每个进窗口的 token 都在分走模型的“注意力预算”。工程目标是：用最小的高信号 token 集合达成目标，而不是把窗口塞满。

05

打个比方

🧰 一张工作台

窗口＝桌面大小。活多时桌上堆满材料，常用的放最顺手的位置（开头），中间的容易“压箱底找不到”。桌子满了，就得收走一部分再继续干。

📒 纪要与原文

不需要每次重听 3 小时录音：把会议写成 1 页纪要（压缩）放桌上，细节要核实时才去翻原文（按需检索）。上下文管理就是这个思路。

06

一个具体场景

长时间数据分析会话如何“续命”
1️⃣

前 5 轮：读 CSV、查分布。样本数据和中间结果都堆在上下文里，一切正常。

2️⃣

第 10 轮：一次查询返回 4 万 token 明细，全灌进窗口——响应变慢，费用变高。

3️⃣

关键信息沉底：用户开头定的“统计口径”被海量工具输出挤到中间，模型开始答偏（U 型效应）。

4️⃣

按需加载：粗结果用 head/tail 只看头部；把结论写进笔记文件，而不是一直留在窗口（Anthropic 称之为 just-in-time + 结构化笔记）。

5️⃣

压缩续命：接近上限时把历史自动压成摘要，保留决策与未解决问题，模型带着摘要继续干活（compaction）。

结论：大窗口是缓冲，不是理由。数据应用的关键仍在于“该进窗口的才进、该滚出的就滚出”。

07

别混淆

边界在哪
🗄️ 上下文窗口Context Window
一次推理的“可见范围”，用完即“忘”，属于工作记忆。
📚 长期记忆向量库 / 文件
在模型外部：数据库、文件、向量库。需要时被检索出来再放回窗口。别把窗口当数据库用。
💬 提示词Prompt
只是上下文的一部分。上下文工程管的是推理全程：系统提示、工具、检索、历史、记忆都要持续维护。
🧮 token 计数
token ≠ 字数：一个词可能拆成多个子词 token，中英文占比也不同，别用“字”去估算窗口。
📶 上下文缓存Context Caching
缓存固定前缀可省“重复读同一段”的钱与时间，但它不扩大可见范围，只是更省钱。
🧨 安全面
塞进窗口的每条文本都可能被当成指令——检索资料、网页内容是提示注入的主要入口，要按“不可信内容”隔离。
  • 一句话边界：先想“哪些 token 必须同时出现”，再选窗口大小；越关键的越靠前，越庞杂的越要“按需检索”，而不是全文灌入。

最小示例

一段伪代码看懂“省着用”

一个省上下文的数据问答循环（伪代码）

def answer(问题):
    基础 = 系统提示 + 最近5轮对话      # 只留最近的历史
    if token数(历史) > 上限*0.8:     # 快满了就压缩
        基础 += 摘要(旧对话)             # 旧的变成摘要，不留原文
    资料 = 检索(问题)                  # 按需取回，不预载全文
    答案 = llm(基础 + 资料 + 问题)
